# V1.1 生产化增强版路线图

## 1. 版本目标

V1.1 的主题是：**持久化权限、多 Provider 路由、可观测性与生产可靠性**。

V1 已经具备基本的 API Key、模型调用和 OpenAI-compatible 接口后，V1.1 不急于增加复杂业务能力，而是把网关提升为可长期运行的内部平台服务：

- 租户或主体可以创建、轮换和吊销 API Key。
- 每个主体只能访问授权模型，并受额度、速率和并发策略约束。
- 一个公开模型可以配置主备 Provider，并在明确的失败场景下切换。
- 请求、错误、延迟、Token 和成本都有可追踪的记录。
- `knowledge-base-server` 可以通过统一客户端稳定使用网关。

## 2. 版本边界

### 必须完成

1. PostgreSQL 数据模型、迁移和初始化数据。
2. API Key 生命周期管理：创建、展示一次、轮换、吊销、过期。
3. 租户/主体/策略模型，以及模型访问权限、速率、并发和 Token 限额。
4. 数据库驱动的模型目录和 Provider registry。
5. 至少两个 Provider 适配器，支持公开模型名到上游模型名的映射。
6. Provider 主备路由、健康状态和可配置故障转移。
7. 分布式限流、并发控制、熔断、退避重试和总 deadline。
8. 审计记录、Prometheus 指标、OpenTelemetry trace 和敏感字段保护。
9. 与 `knowledge-base-server` 的统一客户端和端到端测试。

### 明确不做

- Agent 编排、知识库检索、文档权限和 MCP 工具执行。
- WebSocket 和完整管理后台。
- 复杂账单结算、发票和支付系统。
- Prompt 模板市场或用户自定义工作流。
- 一次性接入大量 Provider；先验证两个 Provider 的抽象。

## 3. 目标架构

```text
HTTP API
  -> Authentication / Principal
  -> Request validation
  -> Policy authorization
  -> Rate + concurrency + quota
  -> Model router
  -> Provider adapter(s)
  -> Audit + metrics + tracing
```

建议模块边界：

- `internal/auth`：API Key 哈希校验、主体解析、Key 生命周期。
- `internal/policy`：模型权限、配额、速率和并发策略。
- `internal/catalog`：公开模型、Provider、能力和路由配置。
- `internal/router`：Provider 选择、健康状态、故障转移和熔断。
- `internal/provider`：各供应商协议适配，不向 HTTP 层泄漏 SDK 类型。
- `internal/limits`：Redis 分布式限流、并发租约和 Token 计数。
- `internal/audit`：请求元数据、错误分类、用量和成本估算。
- `internal/observability`：日志、metrics、trace 和脱敏。

## 4. 数据模型

建议至少包含以下表，字段名可按现有项目风格调整：

- `tenants`：租户状态和显示名称。
- `subjects`：用户、服务账号或其他调用主体。
- `api_keys`：`key_id`、哈希、前缀、主体、状态、过期时间、最后使用时间、创建/吊销时间。
- `model_catalog`：公开模型名、能力、状态和默认限制。
- `providers`：Provider 名称、类型、启用状态、健康检查配置；密钥只来自 Secret Manager 或环境变量。
- `model_routes`：公开模型到 Provider/上游模型的映射、优先级和超时。
- `access_policies`：主体或租户允许的模型、RPM、并发数、Token 上限和策略版本。
- `llm_requests`：request ID、主体、模型、Provider、状态、耗时、输入/输出 Token、错误分类、时间戳。

API Key 只在创建响应中返回明文，数据库保存带随机 salt 的不可逆哈希。审计表默认不保存 prompt 和 completion；如未来支持采样，必须有显式配置、脱敏规则和保留期限。

## 5. 认证与授权流程

请求处理顺序必须固定：

```text
API Key authentication
  -> request/schema validation
  -> model existence and capability check
  -> subject/tenant model authorization
  -> rate, concurrency, and quota checks
  -> provider invocation
```

认证成功后生成 `Principal`，至少包含 `subject_id`、`tenant_id`、`key_id`、角色和策略版本。无权模型返回 403；不存在模型与无权模型的响应不能泄漏策略细节。

建议提供内部管理 API 或 CLI：

- 创建 API Key（明文只返回一次）。
- 列出 Key 元数据（不返回密钥）。
- 轮换并撤销旧 Key。
- 吊销 Key。
- 查看主体当前策略和用量摘要。

管理接口必须独立认证，默认只监听内网或管理端口，不应直接暴露公网。

## 6. Provider 路由与可靠性

公开模型名由网关控制，客户端不得指定任意 Provider、URL 或上游模型。路由配置应包含：

- Provider 和上游模型名。
- 优先级或权重。
- 支持的能力：stream、tools、vision 等。
- 单请求超时和最大 Token。
- 健康状态、启用状态和配置版本。

故障转移规则：

- 仅在请求尚未向客户端产生不可逆输出时切换 Provider。
- 流式响应开始后禁止切换 Provider。
- 重试只针对明确的网络错误、429 和可恢复的 5xx，并受总 deadline 约束。
- 认证失败、参数错误、权限错误和明确的业务拒绝不得重试。
- 熔断器按 Provider 或路由维度统计连续失败，恢复采用半开探测。

V1.1 至少实现一个主 Provider 和一个备用 Provider 的集成测试，包括主 Provider 超时、429、5xx 和恢复场景。

## 7. 限流、并发与额度

Redis 用于多实例一致的速率计数和并发租约；本地内存实现只用于开发或 Redis 不启用的明确单实例模式。限流维度建议支持：

- API Key。
- 主体或租户。
- 模型。

策略至少包含 RPM、并发数、单请求最大输入/输出 Token、每日/月度 Token 上限。上游未提供 Token 用量时记录为未知，不得伪造精确计数。限流响应统一为 429，并包含 `Retry-After`（可计算时）。

## 8. 可观测性与安全

必须提供：

- `requests_total`、`request_duration_seconds`、`upstream_errors_total`、`tokens_total`、`rate_limit_total` 等 Prometheus 指标。
- trace ID 与 request ID 贯穿网关、Provider 和 `knowledge-base-server`。
- 结构化日志，至少包含主体、模型、Provider、状态、延迟和错误分类。
- 日志和审计中不出现完整 API Key、Provider Secret 或默认 prompt/completion。

安全加固至少包括请求体大小、消息数量、消息长度、总 deadline、SSRF 防护和上游响应大小限制。Provider URL 必须来自受信任配置，不能由客户端输入。

## 9. 与 knowledge-base-server 的集成

Python 服务只配置网关 base URL 和内部 API Key，通过独立的 LLM client 调用网关；业务代码不再拼接 Provider URL，也不读取 Provider 密钥。

调用必须传递 `Authorization` 和 `X-Request-ID`，必要时传递租户/用户上下文。网关错误应转换为 Python 的标准错误 envelope，同时保留 request ID。至少覆盖聊天、总结、写作和问答调用链的非流式与流式场景。

## 10. 实施顺序

1. 盘点 V1 当前接口、配置和测试，冻结兼容性约束。
2. 增加 PostgreSQL 迁移、种子数据和 repository 接口。
3. 实现 API Key 生命周期、Principal 和管理 CLI/API。
4. 实现模型目录、Provider registry 和访问策略。
5. 接入第二个 Provider，完成模型路由和故障转移。
6. 加入 Redis 限流、并发租约、熔断、重试和 deadline。
7. 加入审计、metrics、tracing、脱敏和成本估算。
8. 更新 `knowledge-base-server` client，完成端到端联调。
9. 做故障注入、迁移回滚、并发和安全测试，更新部署文档。

每一步都应保持 `go test ./...` 可运行。数据库迁移、Provider 适配和路由策略必须有离线测试，不依赖真实模型调用。

## 11. 验收标准

- API Key 创建、轮换、吊销和过期行为完整且有测试。
- 无效 Key 返回 401，且不会触发 Provider 请求。
- 无权模型返回 403；请求不存在模型时不泄漏授权策略。
- RPM、并发和 Token 限额在单实例和 Redis 多实例模式下符合文档定义。
- 主 Provider 遇到可恢复故障时按策略切换备用 Provider；流式已开始后不切换。
- 超时、429、5xx、客户端取消和上游断流均有明确错误和测试覆盖。
- 审计、日志和 metrics 可按 request ID 关联，且没有明文密钥或默认 prompt。
- `knowledge-base-server` 仅使用网关 client 即可完成主要 LLM 工作流。
- 数据库迁移可升级和回滚；服务重启不会丢失 Key、策略或审计元数据。
- `go test ./...`、静态检查、迁移测试、容器启动检查和端到端测试通过。

## 12. Agent 开工检查清单

- 先阅读 `docs/agent-start.md` 和本路线图，再检查 V1 实际代码，不要假设接口已经完全按文档实现。
- 先冻结兼容性和迁移策略，再修改公开 HTTP 契约。
- 先写认证、授权、路由和故障场景测试，再实现具体 Provider。
- 所有新配置都必须有启动时校验、示例值和安全默认值。
- 不要把 Provider SDK 类型、数据库模型或 Redis 细节泄漏到 HTTP handler。
- 修改接口或数据模型时同步更新集成测试与文档。
- 不要修改 `../knowledge-base-server`，除非当前工作明确属于联调任务。
