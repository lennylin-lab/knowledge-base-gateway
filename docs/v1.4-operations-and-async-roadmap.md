# V1.4 异步推理与运营治理路线图

## 1. 版本目标

V1.4 的主题是：**异步推理、成本治理与运营安全**。

V1.3 已完成模型控制面：Embedding 接口、默认模型、retrieval profile、按
Provider 凭据、多行策略折叠以及能力错误诊断。V1.4 不改变这些模型选择和
能力声明语义，而是补齐长请求、成本结算和生产运营所需的生命周期管理：

- 长时间请求可以持久化、恢复、取消和查询；
- Token 用量能够按价格版本结算为可解释的成本；
- 管理访问从单一静态 token 演进为有角色、有审计的权限模型；
- 审计、结果和用量数据具备留存、归档和导出策略。

本版本仍然是模型网关，不引入 Agent loop、工具执行、业务数据访问或完整
支付系统。

## 2. 前置条件与兼容性原则

- V1.3 的 Chat Completions、Responses、Embeddings、模型发现、默认模型、
  retrieval profile、Provider 凭据和多行策略语义已可用。
- `/v1/chat/completions`、`/v1/responses`、`/v1/embeddings` 的现有同步行为、
  SSE 终止事件、错误 envelope、request ID 和能力门控保持兼容。
- 新字段和新端点采用加法演进；破坏性变化进入 `/v2`。
- 显式传入的 `model` 始终优先于 V1.3 默认模型；异步请求使用与同步请求
  完全相同的认证、模型授权、能力检查、限流、并发和 Token 配额流程。
- 客户端只能选择公开模型名；Provider、上游模型、URL 和密钥不进入公共
  响应或异步任务结果。
- 迁移从 V1.3 的 version 5 继续递增，不修改已应用的迁移。

## 3. V1.4 范围

### 必须完成

1. Responses 后台任务模式、状态查询和取消。
2. 幂等键、任务恢复、结果保留和租户隔离。
3. Provider/模型价格目录、版本化成本账本和预算治理。
4. 管理员凭据生命周期、角色/scope 和管理接口授权。
5. 审计与结果 TTL、归档、导出和大表分区策略。
6. 异步队列、结算、取消、成本未知和运营状态的指标、日志和 trace。

### 暂不完成

- 网关内置 Agent loop、自动执行工具或业务数据库访问。
- 面向最终用户的聊天 UI、Prompt 市场和工作流编辑器。
- 支付、发票、充值和完整商业计费系统。
- WebSocket、跨区域 active-active 和大量 Provider 一次性接入。
- 在单任务异步生命周期稳定前实现批量任务 API 或 webhook。

## 4. 异步 Responses API

### 4.1 创建任务

扩展 `POST /v1/responses`，新增可选字段 `background: true`。同步请求的默认
行为不变。后台请求返回 `202 Accepted`：

```json
{
  "id": "resp_...",
  "object": "response",
  "status": "queued",
  "model": "public-model",
  "created": 0,
  "request_id": "req_..."
}
```

任务状态必须为：`queued`、`running`、`completed`、`failed`、`cancelled`、
`expired`。后台任务仍使用调用方 API Key 的 subject、tenant、策略版本和
模型授权，不得成为绕过同步限流或配额的通道。

### 4.2 查询和取消

- `GET /v1/responses/{id}`：仅允许任务所属 subject 或具备管理 scope 的
  管理员访问。
- `POST /v1/responses/{id}/cancel`：取消排队或运行中的任务；重复取消必须
  幂等，并返回最终可观察状态。
- 任务结果只返回统一网关响应类型，不返回 Provider 私有字段。
- 结果过期后返回稳定的 `response_expired`，不得重新触发 Provider 调用。
- `Retry-After` 用于 queued/running 的查询建议；查询接口不得触发轮询任务。

### 4.3 生命周期与可靠性

- 任务状态转换由数据库或可靠队列持久化，进程重启后可恢复 queued/running
  任务；同一任务最多有一个有效 worker lease。
- Provider 首次输出前失败允许按现有 V1.3 规则重试/故障转移；已有输出后
  不得切换 Provider。
- 客户端取消必须传播到上游 context。取消、完成和失败的竞态按数据库条件
  更新决胜，并只产生一次最终结算。
- `Idempotency-Key` 对创建请求生效：同一 subject 下相同 key 和相同请求
  返回原任务；请求摘要不同返回 `409 idempotency_conflict`。
- 任务结果和工具参数默认不写入日志；结果大小、保留期限和并发 worker 数量
  必须可配置。

建议新增表：

- `async_jobs`：任务 ID、subject/tenant、协议、请求摘要、状态、lease、重试
  次数、过期时间和最终 request ID；
- `async_job_results`：统一响应、错误分类、usage、结果大小和保留期限；
- `idempotency_keys`：subject、key hash、请求摘要、任务 ID、过期时间。

## 5. 成本与用量治理

### 5.1 价格目录

增加版本化的 Provider/公开模型价格目录，至少支持：

- input tokens；
- output tokens；
- reasoning tokens（Provider 报告时）；
- cached input tokens（Provider 报告时）；
- 生效时间、币种和价格版本。

价格以整数微单位保存和计算，禁止使用浮点金额。审计和账本记录实际使用的
价格版本。没有 usage 或没有有效价格时，成本保持 `null`，不得把未知成本
伪造为零。

### 5.2 结算账本

同步和异步请求共用 reserve、settle、release 语义：

```text
预扣金额 = 最终结算金额 + 释放金额
```

结算必须幂等，同一请求最多产生一条最终 usage/cost 记录。结算失败必须可重试
并可观测，不能静默标记为成功。异步任务在 queued 阶段可预扣预算，在取消或
无 Provider 输出时释放；已有输出的任务按已知 usage 结算，未知部分保留为
unknown。

### 5.3 预算

在现有日/月 Token 配额之外，支持 subject 和 tenant 维度的金额预算：

- 日/月预算与 UTC 边界一致；
- 预算检查发生在 Provider 调用前；
- 多行策略继续使用 V1.3 的 min-of-declared 折叠；
- 配置了成本预算但价格未知时返回 `pricing_unavailable`，不能绕过预算；
- `/admin/usage` 增加预算使用率、已知/未知成本和价格版本。

建议新增表：

- `pricing_catalog`：价格、币种、适用模型/Provider 和版本；
- `usage_ledger`：请求/任务、Token、价格版本、金额、结算状态；
- `budget_policies`：subject/tenant 的日/月金额上限。

## 6. 管理身份与授权

保留 `GATEWAY_ADMIN_TOKEN` 作为开发模式和迁移兼容入口；生产模式增加管理
凭据生命周期：创建、轮换、吊销、过期和最后使用时间。管理凭据只保存不可逆
哈希，明文只在创建或轮换响应中展示一次。

管理角色/scope 至少包括：

- `viewer`：查看模型、Provider、策略、审计和用量元数据；
- `operator`：模型/Provider 开关、路由和运行状态操作；
- `billing`：价格、预算和用量导出；
- `platform-admin`：凭据、租户、策略和全部管理操作。

要求：

- 管理接口按 scope 检查，不能继续把所有操作绑定到一个全能 token；
- 租户管理员只能查看所属租户；平台管理员才能查看全局数据；
- 每次变更记录操作者、scope、目标、旧值摘要和新值摘要；
- 管理审计不记录密钥、Provider secret、prompt、completion 或工具参数；
- 管理 API 自身具备独立限流和失败保护。

## 7. 审计、留存与运营观测

- `llm_requests`、`async_jobs`、`async_job_results` 和 `usage_ledger` 支持可配置
  TTL；到期数据先归档，再按策略删除。
- 请求和任务表按创建时间分区，归档/删除不能阻塞在线请求。
- 提供按 `request_id`、`trace_id`、`job_id`、tenant、subject、model 和时间
  范围查询及脱敏导出。
- 增加指标：队列深度、排队时延、任务完成/失败/取消率、worker lease 超时、
  结算重试、成本未知率、预算拒绝和结果过期数。
- 继续提供 Prometheus；补齐 OTLP/OpenTelemetry trace exporter 配置，贯通
  HTTP、队列、worker、Provider、数据库和结算。
- 优雅停机先停止接收新任务，再回收 worker lease；`/readyz` 必须反映数据库、
  Redis、队列和 worker 状态。

## 8. 错误与版本策略

沿用稳定错误 envelope。新增错误码包括：

- `idempotency_conflict`：同一幂等键对应不同请求，HTTP 409；
- `response_not_found`：任务不属于当前调用方或不存在，按信息泄漏策略返回；
- `response_expired`：结果已过期，HTTP 410；
- `pricing_unavailable`：预算或结算需要价格但当前价格未知；
- `budget_exceeded`：金额预算不足，HTTP 429；
- `job_queue_unavailable`：任务队列不可用，HTTP 503。

Chat、Responses 同步和 Embeddings 的现有错误码不变。新增异步字段必须是可选
字段；破坏性状态或响应变化进入 `/v2`。

## 9. 实施顺序

1. 冻结 V1.3 兼容性 golden tests，完成 version 5 到新迁移的升级/回滚测试。
2. 建立 `async_jobs`、结果存储、幂等键和 worker lease 状态机。
3. 增加 Responses 后台创建、查询、取消、恢复和故障注入测试。
4. 增加价格目录、usage ledger、reserve/settle/release 和金额预算。
5. 引入管理凭据、scope、租户隔离和管理操作审计。
6. 实现 TTL、分区、归档/导出和运营指标；接入 OTLP exporter。
7. 在 mock Provider、两类真实适配器和 PostgreSQL/Redis 环境完成端到端验证。
8. 通过 feature flag 灰度异步任务和成本预算，先按模型再按 tenant 开启。

## 10. 验收标准

- V1.3 的 Chat、Responses、Embeddings、默认模型、retrieval profile、能力门控
  和 Provider 凭据测试无回归。
- 异步任务在重复提交、重启、Provider 超时、队列故障、取消竞态下状态一致。
- 任务结果只能被所属 subject/tenant 或授权管理员读取，过期后不可恢复调用。
- 同一幂等键不会创建两个任务或两条最终结算记录。
- Token 和金额预算在单实例、多实例 Redis 模式下不会超卖；基础设施故障不会
  被伪装成预算拒绝。
- 成本可由 Token、价格版本和账本记录重算；未知价格/usage 显式保留 unknown。
- 管理 scope 不能越权，所有变更都有管理审计，响应不含秘密或内容正文。
- TTL、归档和分区操作不影响在线请求；导出遵守租户隔离和脱敏规则。
- `go test ./...`、race、迁移升级/回滚、故障注入、权限矩阵、负载和容器启动
  检查全部通过。
