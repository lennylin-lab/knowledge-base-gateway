# V1.2 统一模型协议与开发者平台路线图

## 1. 版本目标

V1.2 的主题是：**统一模型协议、工具调用与开发者平台**。

V1.1 解决了持久化身份、模型权限、多 Provider 路由、限流、审计和生产可靠性。V1.2 在不破坏现有 `POST /v1/chat/completions` 契约的前提下，统一不同 Provider 的模型能力，让 OpenAI SDK、内部 Agent 和其他客户端都能通过稳定接口使用流式输出、工具调用和结构化输出。

本版本也补足面向开发者和运维人员的模型目录、管理查询、示例和契约测试，但不把网关扩展成 Agent 编排平台。

## 2. 前置条件与兼容性原则

- V1.1 的 API Key、租户/主体、模型目录、Provider registry、路由、限流、审计和 tracing 已可用。
- 现有 `/v1/chat/completions` 请求字段、响应字段、SSE 结束事件和稳定错误 envelope 保持兼容。
- 新能力必须通过模型能力声明和版本化协议启用；不支持的能力应提前返回明确错误。
- 客户端只能选择公开模型名，不能指定 Provider、上游模型名或 URL。
- Provider SDK 类型、数据库模型和内部路由细节不能泄漏到公共 HTTP 契约。
- 工具由调用方或业务服务执行；网关负责协议转换、模型调用和工具调用结果的传输，不执行任意函数或访问业务数据库。

## 3. V1.2 范围

### 必须完成

1. 增加 OpenAI Responses API 兼容接口，同时保留 Chat Completions。
2. 统一非流式和流式事件模型，覆盖文本、工具调用、完成和错误事件。
3. 支持 tool calling、JSON mode 和 structured output 的能力透传与标准化。
4. 提供 `GET /v1/models` 和模型能力详情接口。
5. 为每个 Provider 增加离线 contract tests 和一致性测试。
6. 提供 Go、Python、curl 和 OpenAI SDK 兼容接入示例。
7. 提供模型、Provider、策略、API Key、审计和用量的管理查询接口或 CLI。
8. 增加 mock Provider、协议回放和端到端测试工具。

### 暂不完成

- 网关内置 Agent loop 或自动执行工具。
- 面向最终用户的聊天 UI、Prompt 市场和工作流编辑器。
- WebSocket、跨区域多活和完整商业计费系统。
- 一次性支持所有 Provider 的私有扩展；先覆盖已接入的两个 Provider。
- 将所有旧 Chat Completions 客户端强制迁移到 Responses API。

## 4. 公共 HTTP 协议

### 4.1 Responses API

新增：`POST /v1/responses`。

MVP 支持的请求字段：`model`、`input`、`instructions`、`temperature`、`max_output_tokens`、`stream`、`tools`、`tool_choice`、`response_format`、`metadata`。字段必须经过大小、枚举、嵌套深度和模型能力校验。

非流式响应至少包含：`id`、`object`、`created`、`model`、`status`、`output` 和 `usage`（上游提供时）。响应中的文本、工具调用和拒绝结果都使用稳定的网关类型，不直接返回 Provider 私有字段。

流式响应使用 SSE。建议定义稳定的事件类型：

- `response.created`
- `response.output_text.delta`
- `response.output_text.done`
- `response.function_call_arguments.delta`
- `response.function_call_arguments.done`
- `response.completed`
- `response.failed`

客户端断开必须取消上游 context；上游在首个事件前失败时返回统一错误事件，首个事件产生后不得切换 Provider。

### 4.2 Chat Completions 兼容

继续支持 `POST /v1/chat/completions`，包括当前请求头、OpenAI-compatible JSON、`data: [DONE]` 结束事件和错误 envelope。内部实现可以将两种协议转换到同一个领域请求/事件模型，但不能为了复用而改变现有字段语义。

### 4.3 模型发现

提供：

- `GET /v1/models`：返回调用方有权看到的公开模型列表。
- `GET /v1/models/{model}`：返回模型能力、上下文和输出限制、支持的协议、状态和路由版本。

不得通过模型列表泄漏 Provider 密钥、内部 URL、备用路由细节或其他租户的策略。未知模型和无权模型的错误行为继续遵循 V1.1 的信息泄漏约束。

## 5. 统一领域模型与能力矩阵

HTTP handler 先把 Chat Completions 或 Responses 请求转换为内部领域请求，再交给路由和 Provider。Provider 返回内部响应/事件，最后由协议适配层编码为 JSON 或 SSE。

模型能力至少包括：

- `chat` / `responses`
- `stream`
- `tools`
- `structured_output`
- `json_mode`
- `vision`
- `reasoning`

还需声明上下文长度、最大输出 Token、支持的消息/输入类型、工具数量上限和是否返回 Token usage。能力矩阵是路由约束，不是客户端可以绕过的提示信息：请求声明了模型不支持的能力时，应在调用 Provider 前返回 400/422。

建议内部接口类似：

```go
type ModelRequest struct {
    Model       string
    Input       []InputItem
    Tools       []ToolDefinition
    Stream      bool
    ResponseSpec *ResponseSpec
}

type Provider interface {
    Capabilities(ctx context.Context, model string) (Capabilities, error)
    Complete(ctx context.Context, req ModelRequest) (ModelResponse, error)
    Stream(ctx context.Context, req ModelRequest, emit func(ModelEvent) error) error
}
```

实际接口可以不同，但核心路由、权限、重试和审计层不得依赖某个 Provider SDK 的请求类型。

## 6. Tool calling 与结构化输出

### Tool calling

- 网关校验工具名称、参数 schema、数量、大小和嵌套深度。
- 网关把调用方提供的工具定义转换成 Provider 格式，并把 Provider 的工具调用转换回统一格式。
- 网关不执行工具、不自动重试工具调用、不替调用方保存工具结果。
- 调用方把工具结果作为下一次请求输入传回网关。
- 流式工具参数必须支持增量事件和最终拼接校验；JSON 不完整时返回明确的协议错误。
- Provider 不支持工具调用时，在路由前返回 `capability_not_supported`。

### Structured output / JSON mode

- 支持明确的 JSON schema 版本和大小上限。
- 路由前校验 schema；响应结束后可做 JSON/schema 校验。
- 校验失败必须在审计中记录原因，不能静默把无效文本标记为成功。
- 不同 Provider 的 schema 差异由适配器处理，公共响应保持统一。

## 7. Provider contract tests

每个 Provider 都必须通过同一套离线契约测试。测试使用 mock transport 或录制的 fixture，不调用真实模型，至少覆盖：

- 普通非流式文本响应和 usage 映射。
- 流式文本增量、结束事件和客户端取消。
- 工具调用参数、分片拼接和工具结果回传。
- structured output、JSON mode 和不支持能力的拒绝。
- 上游 400、401、429、5xx、超时和格式异常。
- Provider 私有错误到网关错误类型的映射。

核心路由层另有一套与 Provider 无关的测试，确认新增适配器不需要修改权限、限流、审计和错误处理代码。

## 8. 管理和运营接口

管理接口默认只监听内网或管理端口，并使用独立的管理员认证。建议提供以下只读/运维能力：

- 查看模型目录、能力矩阵和当前路由版本。
- 查看 Provider 启用状态、健康状态、最近错误摘要和熔断状态。
- 查看主体、API Key 和策略元数据（不返回密钥）。
- 按 request ID、租户、主体、模型和时间范围查询审计记录。
- 查询 Token、请求数、错误率、P50/P95 延迟、首 Token 延迟和成本估算。
- 手动启用/禁用模型或 Provider，并记录管理操作审计。

管理响应不得包含 prompt/completion 原文，除非未来增加显式、脱敏、限时的调试采样功能。

## 9. 开发者体验

在 `docs/` 中提供：

- API 版本和兼容性策略。
- curl 的非流式、SSE、tool calling、structured output 示例。
- Python `openai` SDK 通过 `base_url` 接入的示例。
- Go HTTP client 示例和错误处理示例。
- 本地 mock Provider 的启动方式和测试 API Key。
- 常见错误、重试规则、`Retry-After`、request ID 和 trace ID 说明。

示例不得包含真实 Provider 密钥，也不得默认把 prompt 写入日志。所有示例应与自动化 smoke test 共用请求样例，避免文档漂移。

## 10. 异步和长请求（可选增强）

只有在同步请求和流式协议稳定后，才考虑 `POST /v1/responses/{id}/cancel` 或批量任务接口。若 V1.2 实现异步能力，必须明确：

- 任务状态机：`queued`、`running`、`completed`、`failed`、`cancelled`。
- 主体权限、额度预扣和最终 usage 结算。
- 结果保留期限和访问控制。
- 重启、重复提交和取消竞态行为。

异步任务不能成为绕过同步限流、模型权限或审计的后门。

## 11. 版本与发布策略

- `/v1/chat/completions` 和 `/v1/responses` 同属稳定 V1 协议；新增字段必须向后兼容。
- 破坏性字段或语义变化进入 `/v2`，不能通过隐式配置改变 V1 行为。
- 模型能力和 Provider 适配器使用独立版本/配置版本，审计记录保存使用的版本。
- 新能力先以单模型或 feature flag 灰度，再扩大到租户。
- 旧协议至少保留一个明确的弃用周期，并在模型/接口文档中标注。

## 12. 实施顺序

1. 盘点 V1.1 实际公共契约，建立兼容性回归测试和 golden fixtures。
2. 定义领域请求、响应、事件和能力矩阵，先实现 Chat 协议适配而不改变外部行为。
3. 增加 `/v1/responses` 非流式接口和错误映射。
4. 增加 Responses SSE 事件、客户端取消和首事件前故障处理。
5. 实现工具调用、JSON mode、structured output 以及能力预检查。
6. 为现有 Provider 补齐 contract tests，接入第二个 Provider 的统一适配。
7. 增加 `/v1/models`、管理查询、用量查询和管理操作审计。
8. 完善 mock Provider、SDK 示例、OpenAPI 文档和开发者 quickstart。
9. 做协议兼容、故障注入、并发流式、schema 校验和安全测试。

每一步都应保持 `go test ./...` 可运行，并且现有 `knowledge-base-server` client 不需要修改即可继续调用 Chat Completions。

## 13. 验收标准

- 现有 Chat Completions 的非流式、SSE、错误 envelope 和 request ID 行为无回归。
- OpenAI SDK 可以通过配置 `base_url` 和 API Key 调用 `/v1/responses`。
- Responses 非流式和流式事件可以表达文本、工具调用、完成和失败状态。
- 模型能力不支持时，在 Provider 调用前返回稳定的 `capability_not_supported` 错误。
- 至少两个 Provider 通过同一套 contract tests，且路由核心不包含 Provider 特殊分支。
- 工具调用只负责转换和传输，网关不会执行任意工具或泄漏工具参数到日志。
- structured output/schema 校验、流式增量拼接和无效 JSON 均有测试覆盖。
- `/v1/models` 只返回调用方有权访问的模型和公开能力信息。
- 管理查询可以按 request ID 关联审计、metrics 和 trace，且不返回明文密钥或默认 prompt。
- curl、Python、Go 和 OpenAI SDK 示例可在 mock Provider 环境中执行。
- API 版本、弃用策略和 feature flag 行为有文档和自动化测试。

## 14. Agent 开工检查清单

- 先阅读 `docs/agent-start.md`、`docs/v1.1-production-roadmap.md`、`docs/gateway-client-contract.md` 和本路线图。
- 先生成 V1.1 兼容性 golden tests，再修改公共协议或内部领域模型。
- 不要把 Responses API 的字段直接塞进某个 Provider SDK 类型；先经过统一领域模型。
- 不要把工具执行、Agent loop 或业务权限放入网关核心。
- 每新增一个 Provider 能力，都同步更新能力矩阵、contract tests、OpenAPI 和示例。
- 任何新管理接口都要有独立认证、权限检查和管理操作审计。
- 流式协议必须测试客户端取消、上游断流、首事件前失败和首事件后失败。
- 修改协议、错误码或模型能力时同步更新 Python client 集成测试。
- 不要修改 `../knowledge-base-server`，除非当前任务明确属于 V1.2 联调。
